# Offer 大作战 · 约 5 分钟答辩讲稿

有请下一队｜黄淮学院｜白湛文、白龙飞、冯子鑫

## 01

各位评委好，我们是黄淮学院的“有请下一队”，成员是白湛文、白龙飞、冯子鑫。我们带来的项目叫 Offer 大作战：选一个离谱的校园岗位，和有个性的面试官聊四题，最后领到一张带印章的娱乐录用单。

## 02

我们把它定位成校园娱乐游戏。岗位来自大家熟悉的校园生活，例如摸鱼艺术家、食堂品鉴师、早八勇士。体验目标是让人愿意参与、愿意回答，也愿意把结果分享给朋友。产品提供十个岗位、五位角色和三种模式；它不提供真实招聘结论。

## 03

主线很清楚：选择岗位和面试官，完成四次作答，再生成录用单。思考和澄清不占题数，跳过计题，用户也能提前结束。录用单可以实际导出 PNG，而不只是提示用户截图。这页展示的是本地演示界面。

## 04

角色差异不只体现在头像上，也体现在接话方式。赛博判官会抓逻辑漏洞，摸鱼前辈看起来懒洋洋，但会追问具体方案；玄学角色用签文包装岗位问题；诗人先共情，再回到回答；话痨先联想，随后把话题交回来。角色和岗位共同进入可信提示词。

## 05

视频模式中，主画面是角色图的状态动画，小窗是用户自己的镜头预览。面试官先请用户站好，用户明确同意后才上传一张截图看穿搭。解除静音开始录音，再次静音结束并识别；用户能修改识别文字再发送。回复使用语音播放。它是回合式交互，没有宣称全双工通话或精确口型。

## 06

我们还提供了基础反转玩法。用户从回答问题的一方变成面试官，向 AI 应聘者小欧提问，并决定录取或淘汰。后端使用独立的应聘者提示词，不直接复用面试官卡。这个玩法让同一套岗位内容多了一种互动方式。这页是本地演示截图。

## 07

前端使用原生网页技术，浏览器负责交互和媒体生命周期。后端通过 FastAPI 管理会话，保存可信的岗位、角色、阶段和历史，再调用独立适配器。前端不能自己决定评分或结束阶段。四类 AI 能力分别配置和失败处理；部署使用 Docker 与 Caddy，让页面和 API 同源提供 HTTPS 访问。

## 08

结果采用五个一到十分的娱乐维度。真实评价可用时，先按 AI 七成、规则三成混合，四舍五入并限制为整数，再由后端按最终均分判定。规则检查有效且不重复的回答和行动、应变、协作、创意信号，不只奖励长答案。没有有效回答时单独标为未评定；没有模型时使用规则并明确标示演示。

## 09

黑客松现场的体验不能只依赖一次理想请求。我们做了重复提交去重、阶段控制和恢复入口；离开通话时会清理媒体与过期请求。语音识别失败可以打字，语音合成失败保留字幕。上传图片需要明确同意，应用默认不保存原始媒体。网络或 API 不可用时，本地演示题库仍能走到结果，但会告诉用户已经降级。

## 10

当前版本有四十六项后端检查和四十五项浏览器完整回归通过，另有五项不适用于对应引擎的假摄像头场景跳过。真实多轮对话与评价、视觉及语音接口都有独立记录，HTTPS 测试入口已上线。用户已完成手机登录并反馈镜头画面和交互问题，我们进行了第二轮修复；完整真人语音整局和最新手机版表现仍持续复测，不能用模拟媒体代替。

## 11

演示时先打开已登录的页面，选择摸鱼艺术家和摸鱼前辈，完成四题。可以先点一次让我想想，展示题数不变，再用脚本处理、抽查修正、队友确认等虚构答案作答，最后导出 PNG。还有时间就展示反转模式。真实 API 网络不稳时，明确切换到本地演示题库，不把模板回答说成模型调用。访问入口是测试地址，现场讲解者提前完成登录，不在投影中暴露密码。

## 12

后续我们会优先完善手机上的键盘、录音和播放体验，继续根据真实反馈匹配角色声音，再扩充岗位与追问内容。我们希望观众不只看一段聊天，而是愿意亲自应聘一次，并带走自己的录用单。我们的介绍到这里，欢迎评委提问。
